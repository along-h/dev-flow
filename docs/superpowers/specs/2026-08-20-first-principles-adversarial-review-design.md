# 第一性原理与对抗性审查设计

## 目标

在不增加常规用户门控数量的前提下，让 Dev Flow 在开发前验证问题与关键假设，在设计后主动寻找反例，并在交付前提供真实运行证据。

## 核心原则

1. 质量判断层级固定为：用户目标与系统不变量 > PRD 验收标准 > 接口契约 > TDD > 项目规范 > 个人偏好。
2. 第一性原理用于构造正确的问题定义；对抗性审查用于尝试证伪已经形成的方案。
3. 结构校验、语义审查、运行验证是三种不同证据，不可互相替代。
4. 对抗审查嵌入既有门控，不新增常规用户审批节点。
5. 审查深度按风险分级：低风险使用内嵌清单，中高风险或关键共享架构使用独立挑战视角。

## 流程调整

### 需求阶段

PRD 增加第一性原理章节，记录用户结果、成功指标、事实、假设、硬约束、最小方案、非目标与停止条件。每个高影响假设必须有证据或验证计划。

### 架构阶段

TDD 与全局架构在现有用户确认前执行对抗性审查。审查输出 `BLOCK`、`ACCEPT_WITH_RISK` 或 `ACCEPT`。`BLOCK` 必须回到架构修订；其他结论随现有门控呈现。

### 开发阶段

开发者从关键假设和系统不变量派生反例测试，优先覆盖乱序响应、重复提交、权限变化、异常数据、慢网与部分失败等高风险场景。

### 代码审查与交付

审查者可质疑 TDD，不再仅以符合 TDD 为通过标准。最终交付必须包含 typecheck、lint、test、build 等项目实际支持命令的运行结果，以及验收标准映射、未验证风险和回滚条件。

## 风险分级

风险分数使用 `影响 × 发生可能性 × 不确定性`，每项取 1–3：

- 1–8：低风险，由独立审查视角执行限时轻量挑战。
- 9–18：中风险，执行一次独立架构挑战。
- 19–27 或关键共享架构：高风险，执行独立挑战并要求反例测试与回滚方案。

纯命名、排版或个人偏好不得形成阻塞项。阻塞项必须关联可复现反例、违反不变量或明确的高影响风险。

## 产物策略

优先扩展现有 `PRD.md`、`TDD.md`、`GLOBAL-ARCHITECTURE.md` 和 `REVIEW.md`，不为低风险任务增加新文件。所有风险级别的挑战都记录在对应架构产物的“对抗性审查”章节中，风险等级只控制挑战深度。

## 验收标准

- PRD 校验能拒绝缺少第一性原理章节的产物。
- TDD 与全局架构校验能拒绝缺少风险评估和对抗性审查结论的产物。
- REVIEW 校验能拒绝缺少审查依据层级、反例验证或运行证据的产物。
- Agent 指令明确区分事实与假设，并允许审查者挑战 TDD。
- 最终交付规则要求报告实际命令、退出码和未验证项。
- 校验脚本新增行为测试，并验证失败与通过路径。
