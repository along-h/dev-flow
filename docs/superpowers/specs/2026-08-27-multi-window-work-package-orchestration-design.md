# 多窗口工作包编排设计

## 1. 背景

当前多工作流按工作包依次完成组件设计、开发、审查和用户验收。逐包确认可以降低错误扩散，但如果需求、实现、返修和后续工作包都留在同一个会话窗口，会持续累积上下文；当用户要求修改早期工作包时，Agent 还需要重新加载早期决策，容易发生上下文截断和任务串扰。

本设计将“用户是否接受工作包”与“其他独立工作包是否可以开始开发”分离，并以持久化文件、专属窗口和范围租约支持安全并发。

## 2. 目标与非目标

### 2.1 目标

1. 主窗口只负责需求基线、拆包、调度、冲突处理和用户门禁，不承担工作包业务代码实现。
2. 每个工作包可以在专属窗口中设计、开发、审查、返修和恢复上下文。
3. 互不影响的工作包可以在多个窗口同时修改业务代码。
4. 路径、共享资源或依赖发生冲突时，在修改前阻止并发。
5. 用户要求返修时回到原工作包上下文，不污染其他工作包。
6. 被两个或更多工作包使用的公共能力，在满足独立交付条件时提取为共享基础工作包，并支持契约先行的并行开发。
7. 用户确认仍是工作包进入 `ACCEPTED` 的唯一依据；所有工作包完成后仍执行全局回归和最终验收。

### 2.2 非目标

1. 本阶段不自动创建 Git worktree、分支或提交。
2. 本阶段不自动合并多个代码工作区。
3. 不为已有且可以直接复用的公共组件创建额外工作包。
4. 不为了并行把无法独立验证的业务逻辑强行拆开。
5. 不依赖聊天历史作为唯一交接来源。

## 3. 总体架构

采用“一个调度窗口 + 多个工作包窗口”的结构：

```text
主调度窗口
  ├─ WP-SHARED-01 窗口：共享基础契约与实现
  ├─ WP01 窗口：业务包开发、审查和返修
  ├─ WP02 窗口：业务包开发、审查和返修
  └─ WP03... 窗口：按工作包独立扩展
```

主窗口维护工作包依赖图和全局事实。工作包窗口只读取自己的恢复包及其中明确引用的共享产物，不加载其他工作包的完整历史。

```text
.dev-flow/

│   ├── PRD.md
│   ├── TASK-BREAKDOWN.md
│   ├── GLOBAL-ARCHITECTURE.md
│   ├── COMPONENT-INDEX.md
│   └── DESIGN-SOURCES.md
├── work-packages/
│   ├── WP-SHARED-01-shared-filter/
│   │   ├── REQUIREMENTS.md
│   │   ├── DESIGN-SOURCES.md
│   │   ├── COMPONENTS.md
│   │   ├── TDD.md
│   │   ├── REVIEW.md
│   │   ├── EVIDENCE.md
│   │   ├── HANDOFF.md
│   │   └── STATUS.json
│   ├── WP01-user-list/
│   │   └── ...
│   └── WP02-order-list/
│       └── ...
├── runtime/

│   └── write-leases/
│       ├── WP01.json
│       └── WP02.json
└── scripts/
    └── work-package-state.js
```

### 4.1 共享产物

- `PRD.md`：全局需求基线、范围和验收事实。
- `TASK-BREAKDOWN.md`：工作包、消费者集合、依赖图、拥有边界和执行批次。
- `GLOBAL-ARCHITECTURE.md`：跨工作包数据模型、共享契约和契约影响关系。
- `COMPONENT-INDEX.md`：项目已有可复用资源。
- `DESIGN-SOURCES.md`：全局设计源登记及工作包规格索引。

### 4.2 工作包产物

- `REQUIREMENTS.md`：当前包覆盖的 UC、验收标准、范围和非目标。
- `DESIGN-SOURCES.md`：当前包模块设计源、提取完整度和规格引用。
- `COMPONENTS.md`：当前包拥有和引用的组件边界。
- `TDD.md`：当前包技术设计、契约和测试策略。
- `REVIEW.md`：当前包最新审查结果和用户验收交接。
- `EVIDENCE.md`：实际命令、退出码、测试结果和人工验收证据。
- `HANDOFF.md`：新窗口恢复任务所需的最小上下文。
- `STATUS.json`：状态、依赖、拥有范围、消费者、租约和验收轮次。

## 5. 工作包类型与共享基础提取

工作包分为：

- `business`：直接交付业务 UC 的工作包。
- `shared-foundation`：为两个或更多工作包提供公共组件、类型、API 封装、状态能力或其他稳定基础的工作包。

### 5.1 提取条件

公共部分只有同时满足以下条件才提取为 `shared-foundation`：

1. 消费方工作包数量大于或等于 2，使用 `consumers` 集合表示，不设置固定数量字段。
2. 公共能力需要新增或实质修改；已有能力可直接复用时不创建新包。
3. 输入、输出、状态、错误和兼容边界能够形成稳定契约。
4. 可以独立测试、交付和回滚。
5. 提取后不会产生循环依赖，也不要求消费者频繁共同修改契约。

简单辅助逻辑、强耦合业务内部实现和无法独立验收的部分不得为了并行而提取。

### 5.2 拆分算法

1. 依据 UC、状态、接口和独立验收边界形成候选业务工作包。
2. 分析全部候选包之间重复出现的新增或实质修改资源。
3. 按内聚性提取一个或多个共享基础工作包，避免形成单一巨型 `WP00`。
4. 为每个共享基础包记录 `consumers`、拥有路径、共享契约和独立验收标准。
5. 重新计算工作包有向无环依赖图、写入范围和执行批次。
6. 对错误合并、错误拆分、循环依赖和伪共享执行独立挑战。
7. 用户确认工作包边界、业务优先级和共享契约后进入执行。

共享基础包可以依赖其他共享基础包，但全部关系必须保持为有向无环图。

## 6. 状态模型

### 6.1 工作包状态

```text
PLANNED
  ↓
READY
  ↓
IN_PROGRESS
  ↓
IN_REVIEW
  ↓
WAITING_FOR_USER_ACCEPTANCE
  ├─ 用户要求修改 → CHANGES_REQUESTED → IN_PROGRESS
  └─ 用户明确确认 → ACCEPTED
```

补充状态：

- `BLOCKED`：存在外部事实、设计源、依赖或验证阻塞；解除后返回记录的原状态。
- `SCOPE_CHANGE_REQUESTED`：实现需要越过已批准范围，必须停止越界修改并返回主窗口重排。
- `CONTRACT_SYNC_REQUIRED`：依赖的共享契约发生变化，消费方暂停受影响实现并重新同步。

### 6.2 状态约束

1. `ACCEPTED` 只能由主窗口在获得用户明确确认后写入。
2. 代码审查通过、测试通过或用户选择 P1/P2 处理方式不能替代工作包验收。
3. `WAITING_FOR_USER_ACCEPTANCE` 不阻塞无依赖、无范围冲突工作包继续开发。
4. 依赖包未满足相应依赖门禁时，消费方不得进入受限制阶段。
5. 所有状态转换通过确定性脚本执行，非法跳转直接拒绝。

## 7. 共享契约与并行开发

共享基础依赖拆为两个门禁：

- `CONTRACT_APPROVED`：共享 Props、类型、事件、状态、API 和设计规格已经确认。消费方可以依据稳定契约开始并行开发。
- `ACCEPTED`：共享基础实现已经完成审查和用户验收。消费方才能完成真实集成验收并进入自身 `ACCEPTED`。

```text
共享基础契约 CONTRACT_APPROVED
  ├─ 共享基础包实现
  ├─ 消费方 WP01 按契约实现
  ├─ 消费方 WP02 按契约实现
  └─ 消费方 WP03... 按契约实现

共享基础实现 ACCEPTED
  └─ 所有消费者完成真实集成、回归与各自验收
```

消费方只能引用共享基础包拥有的源码和契约，不得修改其拥有路径。契约变化时，主窗口根据 `consumers` 集合将全部受影响工作包转为 `CONTRACT_SYNC_REQUIRED`，展示影响范围并重新确认契约后恢复。

## 8. 并行写入租约

每个工作包声明：

```json
{
  "id": "WP01",
  "type": "business",
  "state": "IN_PROGRESS",
  "ownedPaths": ["src/users/", "src/services/user.ts"],
  "sharedResourceClaims": [
    { "id": "api:user", "mode": "read" },
    { "id": "type:User", "mode": "read" }
  ],
  "dependencies": [
    {
      "workPackageId": "WP-SHARED-01",
      "requiredForDevelopment": "CONTRACT_APPROVED",
      "requiredForAcceptance": "ACCEPTED"
    }
  ],
  "consumers": []
}
```

`ownedPaths` 使用项目根目录下经过规范化的精确文件或目录前缀。`sharedResourceClaims` 表示物理路径之外的逻辑契约访问，例如全局路由、公共类型、Store、API 契约和构建配置。

- `read` 与 `read` 可以并行。
- `write` 与同一资源的任意现存声明冲突。
- 共享基础实现正常进行时依据已批准契约写内部源码，不申请契约 `write`；只有修改已批准契约时才申请 `write`，并触发消费者同步流程。
- `dependencies.requiredForDevelopment` 控制是否可以开始代码开发，`requiredForAcceptance` 控制是否可以进入最终用户验收。

### 8.1 允许并行的条件

申请方只有同时满足以下条件才获得写入租约：

1. 与现存租约的路径不存在相同、父目录或子目录关系。
2. 共享资源访问模式兼容：同一资源只允许多个 `read` 并存，`write` 必须独占。
3. 所需依赖门禁已经满足。
4. 申请范围位于业务项目内部。
5. 当前状态允许修改代码。

### 8.2 原子协调

`work-package-state.js` 在检查并登记租约的短事务内使用 `lease-registry.lock`。事务通过原子创建获得互斥权，写入租约后立即释放，不在开发期间持有全局锁。因此多个无冲突工作包可以同时保有租约并修改业务代码。

租约记录工作包编号、范围、共享资源、取得时间和随机凭证。释放操作必须匹配凭证，其他窗口不能误释放。异常残留租约不按时间自动删除；主窗口展示持有者和影响范围，获得用户明确确认后才能恢复。

### 8.3 范围变化

工作包发现需要修改租约范围外资源时必须：

1. 停止越界修改。
2. 转为 `SCOPE_CHANGE_REQUESTED`。
3. 向主窗口提交新增路径、共享资源和原因。
4. 重新判断工作包边界、依赖和当前租约冲突。
5. 用户确认范围变化后更新拆分结果并重新申请租约。

## 9. 窗口恢复协议

1. 主窗口创建工作包目录、初始 `STATUS.json` 和 `HANDOFF.md`。
2. 工作包窗口启动时只读取 `STATUS.json`、`HANDOFF.md` 及其中明确列出的共享产物。
3. `HANDOFF.md` 必须包含当前目标、已确认决策、范围、禁止越界项、当前问题、下一动作、风险、证据位置和共享契约版本。
4. 开发、审查、返修、范围变化或等待验收前必须刷新交接文件。
5. 工作包窗口不得重新执行完整需求访谈，也不得读取无关工作包的完整历史。
6. 交接内容与实际代码或共享契约不一致时停止执行，转回主窗口同步，不依据旧对话猜测。
7. WP01 被要求返修时回到 WP01 专属窗口，根据最新 `REVIEW.md`、`HANDOFF.md` 和 `STATUS.json` 恢复。

## 10. 调度规则

主窗口按以下顺序判断工作包是否可派发：

1. 需求基线和任务拆分已经通过用户门禁。
2. 当前包为共享基础包时，契约已经达到执行所需状态。
3. 当前包为消费方时，依赖的契约或实现门禁满足当前阶段要求。
4. 预申请的路径和共享资源与现存租约无冲突。
5. 当前包的设计源状态满足开发入口门禁。
6. 当前包存在可恢复的交接文件。

无依赖且无冲突的多个包可以同时处于 `IN_PROGRESS`。任一包进入 `WAITING_FOR_USER_ACCEPTANCE` 时，主窗口仍可派发其他独立工作包。依赖该包最终实现的工作包，只能在对应门禁满足后推进。

## 11. 用户门禁与交付

每个工作包完成审查和修复回环后，主窗口向用户呈现：

- 变更摘要和修改范围。
- 覆盖 UC 与验收标准映射。
- 实际测试命令、退出码和结果。
- 未验证项、残余风险和回滚条件。
- 共享契约及消费方影响。

用户要求修改时，工作包进入 `CHANGES_REQUESTED` 并返回原窗口。用户明确确认后进入 `ACCEPTED`，并解锁等待其实现门禁的消费方。

所有工作包完成后仍执行全局 typecheck、lint、test、build 和跨工作包回归。逐包验收不能替代最终整体验收。

## 12. 异常处理

| 场景 | 处理 |
|------|------|
| 两个窗口同时申请冲突范围 | 原子租约事务只允许一个成功，另一个保持等待并返回冲突详情 |
| 工作包需要越界修改 | 转为 `SCOPE_CHANGE_REQUESTED`，停止修改并重新编排 |
| 共享契约发生变化 | 所有受影响消费者进入 `CONTRACT_SYNC_REQUIRED` |
| 窗口异常关闭留下租约 | 主窗口展示租约和影响，用户确认后恢复 |
| 交接文件与代码不一致 | 停止恢复，返回主窗口重新生成交接 |
| 形成循环依赖 | 回退任务拆分，重新划分共享基础和业务边界 |
| 共享基础无法独立验收 | 取消独立包，合并到内聚业务边界 |
| 用户未确认工作包 | 保持 `WAITING_FOR_USER_ACCEPTANCE`，不得写为 `ACCEPTED` |

## 13. 兼容策略

1. `multi-workstream` 强制使用 `.dev-flow/work-packages/{工作包}/`。
2. `single-workstream fast` 保持精简会话路径，不强制生成完整目录。
3. `single-workstream standard` 和 `rigorous` 使用 `WP01/`，支持窗口恢复。
4. 旧 `.dev-flow/artifacts/COMPONENTS.md`、`TDD.md` 和 `REVIEW.md` 不自动删除或覆盖。
5. 检测到旧产物时建立只读引用或提示用户迁移。
6. 状态和租约采用临时文件加原子替换，避免异常中断留下半份 JSON。
7. 所有运行状态都位于已被 `.gitignore` 排除的 `.dev-flow/`。

## 14. 确定性脚本接口

新增 `.dev-flow/scripts/work-package-state.js`，支持：

```text
init <工作包>
status <工作包>
transition <工作包> <目标状态>
claim <工作包>
release <工作包> <租约凭证>
recover-lease <工作包>
validate <工作包>
```

脚本必须使用非零退出码拒绝非法状态、路径冲突、共享资源冲突、依赖未满足、凭证错误和未经确认的残留租约恢复。命令输出使用结构化 JSON，供主窗口和工作包窗口读取。

## 15. 验证策略

### 15.1 脚本测试

1. 工作包初始化创建完整目录和有效状态。
2. 合法状态转换通过，非法跳转被拒绝。
3. 未提供用户确认依据时不能进入 `ACCEPTED`。
4. 独立路径和兼容的共享资源读声明允许多个租约并存。
5. 相同文件、相同目录及父子目录冲突被拒绝。
6. 物理路径不同、共享资源相同且均为 `read` 时允许并行；任一方为 `write` 时拒绝。
7. 未满足开发门禁的租约申请被拒绝，未满足验收门禁的最终验收转换被拒绝。
8. 多进程同时申请冲突范围时只有一个成功。
9. 越界范围触发 `SCOPE_CHANGE_REQUESTED`。
10. 错误租约凭证无法释放其他工作包的租约。
11. 残留租约恢复缺少用户确认依据时被拒绝。
12. 原子写入中断后不存在半份 JSON。

### 15.2 工作流验证

1. WP01 和 WP02 修改独立模块时可以在不同窗口同时开发。
2. WP01 验收返修回到 WP01 窗口，不要求主窗口加载完整实现历史。
3. 任一窗口丢失上下文后可仅凭工作包恢复包继续。
4. 共享基础契约确认后，任意数量消费者可以并行实现。
5. 共享基础未 `ACCEPTED` 时，消费者不能完成真实集成验收。
6. 共享契约变化会影响 `consumers` 集合中的全部工作包。
7. 用户未明确确认的工作包始终不能进入 `ACCEPTED`。
8. 全部包完成后仍执行全局回归和最终用户验收。

## 16. 完成标准

满足以下条件视为本能力完成：

1. 每个标准或严格工作包具有独立、可校验、可恢复的目录。
2. 主窗口与工作包窗口职责明确，业务代码上下文不会集中到主窗口。
3. 多个无冲突窗口能够同时取得范围租约并修改业务代码。
4. 路径、共享资源和依赖冲突在修改前被阻止。
5. 公共能力按消费者数量大于或等于 2 的通用集合模型提取，不包含固定数量假设。
6. 共享基础和任意数量消费方可以在契约批准后并行开发。
7. 状态、交接、返修、逐包验收和最终回归形成完整闭环。
8. 不自动执行任何 Git 操作。
