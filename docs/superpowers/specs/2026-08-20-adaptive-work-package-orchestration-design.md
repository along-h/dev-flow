# 自适应工作包编排设计

## 目标

Dev Flow 先基于用户提供的 UC 文档、设计稿和项目上下文收敛需求，再按可独立实现与验证的工作包拆分任务，最后从执行拓扑和治理深度两个维度选择编排方式。

该调整解决两个问题：

1. 不再将页面数量或 UC 数量直接等同于开发任务数量。
2. 不让简单任务在最终路由前被迫承担完整 PRD、全量扫描和多轮门控成本。

## 第一性原理

编排的目标是在质量底线不下降的前提下，最小化流程成本、Agent 协作成本、返工风险和故障损失。

以下概念必须分离：

| 概念 | 定义 |
| --- | --- |
| 页面 | UI 展示与交互容器 |
| UC | 用户为达成目标执行的行为场景 |
| 工作包 | 可以独立实现、验证和交付的一组内聚改动 |
| 架构边界 | 共享状态、数据模型、接口契约和系统不变量的边界 |

UC 是需求与验收的表达单位，不是默认的开发循环单位。多个 UC 可以归入一个工作包；一个 UC 也可以因跨越多个架构边界而拆成多个工作包。

## 两阶段分诊

### 阶段一：初步接入

入口只确定需求发现深度，不确定最终编排模式。输入包括 UC 文档、设计稿、用户说明和可访问的项目上下文。

输出必须包含：

- 已知输入和信息来源。
- 缺失信息与事实/假设冲突。
- 权限、异步提交、共享契约、不可逆操作等硬风险信号。
- `light`、`standard` 或 `deep` 需求发现深度。
- `finalRoute: pending`。

### 阶段二：需求基线后的最终编排

需求基线经用户确认后，Orchestrator 才拆分工作包并决定最终编排。需求不需要消除全部未知项，但高影响未知项必须已确认或具有验证计划。

## 需求拆分就绪条件

进入工作包拆分前，需求基线至少满足：

- 每个 UC 有用户目标、触发条件和前置条件。
- 主流程、异常流程和关键状态变化明确。
- 设计稿覆盖适用的正常、加载、空、错误、禁用和权限状态。
- 验收标准可观察、可验证。
- 范围和非目标明确。
- 事实与假设分离。
- 高影响未知项已有证据或验证计划。

简单任务可以使用精简需求摘要；复杂任务使用完整 PRD。完整度由决策所需信息决定，而不是固定文档长度决定。

## 工作包拆分

工作包按以下问题聚合或拆分：

1. 是否共享同一套状态、数据模型和接口契约？
2. 是否必须一起实现才能完成有效验证？
3. 是否可以独立开发、测试、交付或回滚？
4. 是否存在不同的架构边界、依赖顺序或并行价值？

每个工作包必须记录覆盖的 UC、范围、依赖、共享契约、验收标准和回滚边界。Task Decomposer 提出候选拆分，Orchestrator 对最终拆分和编排决策负责。

## 二维编排模型

### 执行拓扑

- `single-workstream`：一个内聚工作包，一次架构设计、开发和整体验证；内部可包含多个页面或多个 UC。
- `multi-workstream`：存在多个可独立验证的工作包，并且需要依赖排序、共享基础设计或分批交付。

### 治理深度

- `fast`：目标和验收明确、影响局部、可逆、无共享契约或高风险状态变化。
- `standard`：存在有限需求不确定性、局部架构决策、异步交互或中等影响。
- `rigorous`：高不确定性、高影响、跨架构边界、权限安全、复杂状态或关键共享基础。

多工作流至少使用 `standard`。执行中发现隐藏复杂度时只允许升级，不自动降级。

## 编排结果

最终路由结果保存在既有 `TASK-BREAKDOWN.md` 中，避免为低风险任务新增独立产物。结果至少包含：

```json
{
  "ucCount": 4,
  "workPackageCount": 1,
  "topology": "single-workstream",
  "governance": "standard",
  "reason": ["所有 UC 共享页面状态和订单模型"],
  "upgradeTriggers": ["发现需要修改全局订单契约"]
}
```

对于明确的单工作包快速任务，Orchestrator 可以在会话中生成同结构的精简拆分结果，不要求创建完整 PRD、TDD 或 TASK-BREAKDOWN 文件。

## Agent 职责

- Requirements Analyst：根据 UC 文档、设计稿和用户反馈形成需求基线，维护事实、假设和拆分就绪状态。
- Task Decomposer：将 UC 聚合为候选工作包，分析依赖和执行顺序，不再执行“一 UC 一任务”。
- Orchestrator：确认需求基线、批准工作包边界、选择执行拓扑和治理深度。
- Architect：按工作包或共享架构边界设计，不按 UC 数量重复输出 TDD。
- Developer：按工作包实现，并维护 UC 到测试的覆盖映射。
- Code Reviewer：挑战工作包边界、路由结论和风险等级，并验证交付证据。

## 对抗性约束

- 一个页面包含多个共享状态的 UC，不足以触发多工作流。
- 一个 UC 跨越多个可独立验证的架构边界，可以触发多工作流。
- 多页面的同源原子修改可以是单工作包，但必须按影响面回归。
- 单文件权限或提交逻辑修改仍可触发 `rigorous`。
- 工作包无法独立验收时不得为了并行而强行拆分。
- 结构校验不能替代语义审查和实际运行验证。

## 验收标准

- 主 Skill 不再用 UC 数量直接决定编排模式。
- 需求阶段输出拆分就绪判断。
- 任务拆分模板支持工作包、UC 映射和二维编排结果。
- 单页面多 UC 共享状态场景被判定为单工作流。
- 单 UC 跨多个独立架构边界场景可以被判定为多工作流。
- 快速路径仍包含针对性测试、审查和交付证据。
- README、manifest、Agent 指令和模板术语保持一致。

## RED 基线证据

独立评估 Agent 严格应用旧规则后得到：

| 场景 | 旧规则结果 | 失败模式 |
| --- | --- | --- |
| 同一订单页 4 个共享状态且必须整体验收的 UC | 多 UC，拆成 4 个任务 | 强耦合行为被错误拆分 |
| 1 个第三方登录 UC 跨可独立验证的权限与回调边界 | 单 UC，保持 1 个任务 | 独立架构边界被错误合并 |
| 5 个页面回归同一个 Token 文件原子修改 | 多 UC，形成 5 个页面任务 | 回归范围被误当成任务数量 |

重复失败模式是将 UC/页面数量直接当成任务拓扑，而不是检查状态、契约、独立验收和回滚边界。
