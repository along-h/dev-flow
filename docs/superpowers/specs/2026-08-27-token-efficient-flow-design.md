# Dev Flow Token 效率优化设计

## 1. 背景

当前 Dev Flow 在标准和严格治理路径中，会让 Architect、Developer、Reviewer 重复读取完整 PRD、TDD、组件索引、设计源和运行证据。多工作包又按 WP 串行推进，复审轮次可能重新检查全部上下文。结果是普通需求也可能在 WP01 内持续数小时，并产生较高 Token 消耗。

本设计在不削弱真实 P0、安全、权限、异步竞态和共享契约门禁的前提下，通过项目级资产分离、工作包上下文切片、增量复审和更准确的治理路由降低重复读取。

## 2. 目标与非目标

### 2.1 目标

1. 项目组件索引跨需求复用，不与单次需求产物混放。
2. 每个工作包具有独立、可恢复的最小上下文入口。
3. Architect、Developer、Reviewer 默认只读取当前工作包需要的资料。
4. 第二轮及以后只复审未关闭问题、本轮变更和相关证据。
5. P1 不因未修改自动升级为 P0，升级必须有新的高影响证据。
6. 局部、可逆且无硬风险的需求稳定进入 `fast` 路径。
7. 旧版 `.dev-flow/artifacts/` 产物保持只读兼容，不破坏已有运行。

### 2.2 非目标

1. 不在本轮实现多窗口并行、文件租约或自动工作包调度。
2. 不取消 TDD、架构对抗审查、代码与交付质量审查或用户验收。
3. 不降低权限、安全、不可逆操作、复杂异步状态和关键共享契约的治理深度。
4. 不自动修改全局安装目录；仓库版本完成后由用户重新安装或同步 Skill。
5. 不执行任何 Git 操作。

## 3. 方案选择

采用“结构化上下文切片 + 增量复审”的平衡方案。

仅精简提示词无法约束 Agent 的实际读取范围；完整多窗口状态机又会引入超出当前目标的运行复杂度。本方案通过明确目录、输入清单和复审触发器，使 Token 优化成为可验证的流程契约。

## 4. 目录与生命周期

```text
.dev-flow/
├── project/
│   ├── COMPONENT-INDEX.md
│   └── SCAN-META.json
├── runs/
│   └── {需求编号}/
│       ├── PRD.md
│       ├── TASK-BREAKDOWN.md
│       ├── GLOBAL-ARCHITECTURE.md
│       ├── DESIGN-SOURCES.md
│       └── work-packages/
│           └── WP01/
│               ├── HANDOFF.md
│               ├── COMPONENT-SLICE.md
│               ├── COMPONENTS.md
│               ├── TDD.md
│               ├── REVIEW.md
│               └── EVIDENCE.md
└── scripts/
```

### 4.1 项目级资产

- `COMPONENT-INDEX.md` 保存项目已有组件、Hooks、工具函数、内部包和精确导入路径。
- `SCAN-META.json` 保存扫描时间、项目根路径、源码指纹和索引版本。
- 项目级资产只在源码指纹变化时增量刷新，不因创建新需求而全量重建。

### 4.2 需求级资产

- `PRD.md`、`TASK-BREAKDOWN.md`、`GLOBAL-ARCHITECTURE.md` 和 `DESIGN-SOURCES.md` 属于单次需求运行。
- `{需求编号}` 使用稳定、文件系统安全的标识；没有外部编号时由 Orchestrator 生成时间戳加短语义名。

### 4.3 工作包资产

- 每个 WP 独立保存组件设计、TDD、审查和证据。
- Agent 不得把其他 WP 的完整资料复制到当前目录。
- 跨 WP 共享契约通过需求级 `GLOBAL-ARCHITECTURE.md` 引用。

## 5. 最小上下文协议

### 5.1 HANDOFF.md

`HANDOFF.md` 是每个执行 Agent 的默认入口，必须包含：

1. 当前目标和覆盖 UC。
2. 当前范围、非目标和禁止越界项。
3. 已确认决策和接口契约。
4. 系统不变量和未关闭风险。
5. 当前阻塞项或待修复问题。
6. 允许读取的文件、相关章节及读取理由。
7. 当前代码范围和测试范围。
8. 下一步动作与停止条件。

主 Agent 在阶段切换和复审前更新该文件。下游 Agent 先读 `HANDOFF.md`，只有其中列出的资料可以默认读取。

### 5.2 读取策略

每个引用记录以下字段：

| 字段 | 含义 |
|------|------|
| 路径 | 文件或目录的精确路径 |
| 读取模式 | `section` / `targeted` / `full` |
| 范围 | 章节、符号、文件列表或搜索词 |
| 理由 | 当前任务为什么需要它 |
| 失效条件 | 哪种变化要求重新加载 |

默认读取模式为 `section` 或 `targeted`。只有下列情况允许 `full`：

- 接口契约或系统不变量发生冲突；
- 当前修改越过已批准范围；
- 相关章节不足以判断真实 P0；
- 全局回归或最终交付需要完整证据；
- 目标文件较小且切片会丢失必要语义。

Agent 扩大读取范围时必须在输出中记录触发原因，不得以“保险起见”为由读取全部产物。

## 6. 组件索引切片

### 6.1 完整索引

Scanner 继续使用确定性扫描和增量 diff 维护 `.dev-flow/project/COMPONENT-INDEX.md`。已有索引且源码指纹未变化时直接复用。

### 6.2 COMPONENT-SLICE.md

工作包进入组件设计前，根据模块路径、业务关键词、候选组件名和依赖边界生成切片。切片只包含：

- 当前 WP 可能复用的组件；
- 相关 Hooks 和工具函数；
- 精确导入路径和关键 Props；
- 可复用性结论及证据来源；
- 完整索引版本和生成条件。

Architect、Developer、Reviewer 默认读取切片。只有切片没有候选项、候选冲突或发现可能重复实现时，才定向查询完整索引；不直接全文加载。

## 7. 治理路由

### 7.1 fast

同时满足以下条件时默认使用：

- 验收明确；
- 影响局部且可逆；
- 不修改共享契约；
- 不涉及权限、安全或不可逆操作；
- 不包含高风险异步状态变化；
- 修改和测试范围可以定向确定。

`fast` 使用精简需求基线、`HANDOFF.md`、组件切片、针对性测试和一次聚焦审查，不生成不必要的完整 COMPONENTS/TDD 文档。

### 7.2 standard

用于有限架构决策、中等影响或普通异步交互。保留 TDD、一次轻量架构对抗审查和完整首轮代码与交付质量审查，但所有 Agent 仍遵守最小上下文协议。

### 7.3 rigorous

用于权限、安全、不可逆操作、复杂状态、关键共享基础或高不确定性。允许按触发条件读取更多上下文，但不得无理由全文重读所有产物。

执行中发现硬风险时只允许升级，不自动降级。

## 8. 增量复审

### 8.1 第一轮

第一轮代码与交付质量审查覆盖当前 WP 的完整变更范围、验收标准、风险、测试和运行证据。审查问题使用稳定编号，记录级别、证据、修复条件和关联文件。

### 8.2 第二轮及以后

默认输入限制为：

1. 上轮未关闭的 P0 或架构 Blocker；
2. 用户已确认需要修改的 P1/P2；
3. 本轮修改文件和差异摘要；
4. 与问题直接相关的 TDD 章节；
5. 新增、失败或受影响的测试证据；
6. 上轮问题状态表。

Reviewer 先验证旧问题是否关闭，再检查本轮修改是否引入同一影响范围内的新问题。不得重新输出已经关闭且未受影响的问题。

### 8.3 恢复完整审查的触发器

- 修改 API、共享类型、路由、权限或全局状态契约；
- 修改范围超出当前 WP；
- 出现新的构建、类型或回归测试失败；
- 修复改变系统不变量或回滚策略；
- 有证据表明切片遗漏了高影响依赖。

触发后必须记录原因和新增范围。

### 8.4 分级与升级

- P0：功能缺陷、安全漏洞、数据错误、明确竞态、严重性能问题或违反系统不变量，必须修复。
- P1：维护性、局部架构或有限风险问题，由用户决定是否修复。
- P2：可选优化。
- P1 未修复、部分修复或用户选择暂不修复，不会自动升级为 P0。
- 只有出现新的可复现反例、影响升级或违反上位证据时，才允许 P1 升级为 P0，并必须记录新证据。

第三轮仍有 P0 时暂停自动回环，汇总根因、已尝试修复和剩余风险，请求人工判断。

## 9. Agent 职责变化

### 9.1 Orchestrator

- 创建需求和工作包目录；
- 维护 `HANDOFF.md`；
- 决定允许读取的资料和模式；
- 记录扩大上下文的触发原因；
- 保证治理升级不丢失硬风险。

### 9.2 Scanner

- 维护项目级完整索引和扫描元数据；
- 为 WP 生成组件切片；
- 无变化时跳过 AI 语义补充。

### 9.3 Architect

- 先读 HANDOFF 和组件切片；
- 只回查与组件边界、契约和风险直接相关的完整章节；
- 不复制全局资料到工作包产物。

### 9.4 Developer

- 只读取当前 WP 的技术决策、风险、组件切片和设计规格；
- 修复轮次只处理已批准问题，不顺带重构无关代码；
- 更新变更摘要和受影响测试证据。

### 9.5 Reviewer

- 首轮完整、后续增量；
- P1 升级必须有新证据；
- 区分未修复问题、新增问题和已关闭问题；
- 命中完整复审触发器时说明原因。

## 10. 兼容与迁移

1. 初始化新项目时创建 `project/` 和 `runs/`，不再把新产物写入顶层 `artifacts/`。
2. 检测到旧 `.dev-flow/artifacts/COMPONENT-INDEX.md` 时，将其作为只读来源生成新项目索引；不自动删除或覆盖旧文件。
3. 检测到旧 PRD、TDD 或 REVIEW 时，以只读引用方式建立一次迁移运行目录。
4. 校验器在迁移期同时接受旧路径和新路径，错误信息优先展示新路径。
5. README、SKILL、Agent 指令、模板和 CLI 初始化结果必须使用同一目录约定。
6. 仓库版本验证完成后，明确提示用户重新安装或同步全局 Skill，防止继续加载旧副本。

## 11. 错误处理

| 场景 | 处理 |
|------|------|
| HANDOFF 缺失或失效 | 停止当前 Agent，返回 Orchestrator 重建 |
| 组件切片无匹配项 | 定向查询完整索引，不直接全文加载 |
| 切片与源码冲突 | 刷新项目索引和切片后再继续 |
| 修复越过 WP 范围 | 暂停并返回任务拆分或共享架构阶段 |
| 增量复审出现全局失败 | 记录触发器并恢复完整审查 |
| 第三轮仍有 P0 | 停止自动修复，提交人工判断 |
| 旧产物无法映射 | 保持只读，报告缺失信息，不猜测迁移 |

## 12. 验证策略

### 12.1 确定性测试

1. 初始化创建 `project/`、`runs/` 和工作包目录。
2. 旧 `artifacts/` 目录仍可被识别且不会被覆盖。
3. HANDOFF 缺少目标、范围、读取清单、风险或下一动作时校验失败。
4. COMPONENT-SLICE 缺少索引版本、来源、导入路径或生成条件时校验失败。
5. 组件索引未变化时不会重新生成 AI 语义字段。
6. 复审报告能区分未关闭、已关闭和新增问题。
7. P1 未修改不会自动变为 P0。
8. P1 出现新高影响证据时允许升级并要求记录证据。
9. 命中完整复审触发器时必须记录原因和扩大范围。

### 12.2 工作流验证

1. 一个局部可逆需求稳定进入 `fast`，不生成完整 TDD。
2. 一个普通 `standard` WP 的 Architect、Developer、Reviewer 只读取 HANDOFF 所列资料。
3. 第二轮复审只处理剩余问题、本轮变更和相关测试。
4. 权限或共享契约变化能够升级治理并恢复必要的完整审查。
5. 新需求复用项目索引，不重新执行全量扫描。
6. 历史运行能通过只读兼容路径恢复。

### 12.3 验收指标

- 同一项目的第二个需求不再全量生成组件索引。
- 第二轮复审输入不包含未受影响的完整 PRD、TDD 和组件索引。
- 没有新证据时，P1 不会升级为 P0。
- `fast` 路径只产生必要的精简产物。
- 所有真实 P0 和硬风险仍能阻止交付。
- Token 改善通过相同需求前后对比评估；至少记录 Agent 读取文件数、完整读取次数、审查轮次和产物大小，不虚构模型侧精确 Token 数。

## 14. 完成标准

1. 新目录约定、旧路径兼容和初始化行为有自动测试覆盖。
2. HANDOFF 与组件切片具有模板和结构校验。
3. 四个执行角色的默认读取规则改为最小上下文。
4. 首轮完整、后续增量的复审规则在 Skill、Reviewer 和审查模板中一致。
5. P1 自动升级规则被移除，新证据升级规则有测试和说明。
6. `fast`、`standard`、`rigorous` 的上下文和审查深度边界明确。
7. Skill 快速校验、安装检查、模板校验和项目测试完成。
8. 交付说明明确全局旧 Skill 需要重新安装或同步。
