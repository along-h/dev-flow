# Dev Flow v2 精简编排设计

## 1. 目标

Dev Flow v2 从产物和格式完整性优先，调整为用户结果、变更边界和真实风险优先。

1. 删除按出现次数、代码行数或固定技术分层拆组件与 Hook 的机械规则。
2. 状态归属到能维护其不变量的最小必要所有者，不默认提升到页面容器。
3. memoization 只由测量结果或稳定引用契约触发。
4. 需求分析后按可独立交付边界拆工作包，并安全并行无依赖工作包。
5. 需求阶段只用已有设计稿补充需求；进入 UI 开发前，让用户选择补充具体设计稿或按现有依据继续。
6. v2 新运行不生成设计覆盖矩阵，也不依赖 components-readiness。
7. 显著减少默认加载的提示词、产物、重复审核和用户等待。

## 2. 非目标

- 不删除旧版 Rigorous 模板、产物和校验器。
- 不破坏既有 .dev-flow/runs 产物的读取与校验。
- 不为并行而强拆共享状态、共享写入或修改同一文件的任务。
- 不用流程精简代替真实测试、类型检查、Lint 和适用构建。

仓库中不存在可修改的 `AGENTS.md`。v2 会删除自身活动提示词里的机械拆分规则，并在 README 给出替代建议；如果宿主项目或运行环境仍注入“超过固定行数就抽 Hook”等上位指令，使用者还需要在对应项目中同步删除或改写该规则。

## 3. 当前问题

### 3.1 代码边界被机械指标驱动

Architect 把出现两次直接作为公共抽取条件，默认页面容器管理数据并提升共享状态。Developer 固定按类型、API、Hook、组件分层实现。Reviewer 又用重复次数、函数行数和是否使用 memoization 审查。相同规则分散在主 Skill、Agent、模板和测试中，修改单点不能改变最终行为。

### 3.2 表面并行、实际串行

主流程允许安全工作包并行，却又要求当前工作包经用户验收后才能开始下一个，导致同一并行批次被串行化。

### 3.3 Fast 仍背负重型概念

默认上下文重复解释 scheduleVersion、HANDOFF、DESIGN-SOURCES、设计覆盖矩阵、两阶段校验和逐项确认。即使最终走 Fast，Agent 仍需理解并排除大量旧路径。

### 3.4 测试过度绑定文案

部分流程测试检查指定短语和顺序，鼓励多文件重复规则，也让精简文案产生大量测试噪音。

## 4. v2 流程

```text
用户需求与已有设计资料
        ↓
需求分析：目标、范围、行为、验收
        ↓
工作包拆分：所有权、依赖图、并行批次
        ↓
共享基础批次（仅存在共享契约时）
        ↓
当前 UI 批次的设计选择门禁
        ↓
无依赖工作包并行开发与定向验证
        ↓
批次集成、条件 Review、统一交付
```

### 4.1 需求分析

- 需求阶段形成可验证的目标、范围、主要行为和验收标准。
- 需求不清时，Requirements Analyst 用 grilling 询问会改变交付结果的决策。
- 用户已提供的设计稿只用于理解页面范围、文案、交互和状态，不判断是否足以开发。
- 不递归提取全部可见组件，不因缺少组件级节点中断需求分析。

### 4.2 工作包拆分

独立工作包必须具有明确交付结果，能够独立实现、验证和回滚，不依赖其他工作包未确定的内部细节，并且不与同批工作包修改同一文件或共享写入边界。

拆分结果记录目标、范围、非目标、拥有和引用边界、dependsOn、并行批次、验收和回滚方式。页面数、UC 数、目录数和预计代码量都不是工作包边界。

### 4.3 并行批次

- 有共享契约时，第 0 批只确定最小共享类型、API、状态或稳定 UI 契约。
- 同一批无依赖、无共享写入且文件不冲突的工作包按可用 Agent 容量并行。
- 同一批不使用逐工作包启动前验收门禁。
- 用户只在需求基线、工作包方案、批次设计选择、共享契约变化和最终交付等真实决策点确认。
- 新冲突只暂停受影响工作包，并重新安排后续批次。

### 4.4 开发前设计选择门禁

这是用户决策，不是 Agent 主观判断设计完整性。当前批次含 UI 工作包时，Orchestrator 在 Developer 写测试或代码前统一询问：

> 以下工作包即将进入开发：{WP 列表}。是否提供这些模块的具体设计稿，还是按照目前已有的需求资料、设计稿和项目视觉规范继续？

处理方式：

- provided-specific：用户选择补充具体设计稿，对应 UI 工作包等待资料。
- use-current-basis：用户选择按已有依据继续，Developer 直接开发，不再因纯视觉细节追问或阻塞。
- 同一批不同工作包可以选择不同模式。
- 多个工作包由 Orchestrator 合并询问一次，不由各 Developer 分别打断用户。
- 非 UI 工作包跳过该门禁。
- 后续只有业务行为、数据契约或验收标准缺失时重新询问，不以设计稿粒度不足为由追问。

PLAN 只记录 designMode、适用工作包、具体设计链接或项目视觉基线路径，以及必要的人工视觉验收项。

v2 新运行不生成设计覆盖矩阵、DESIGN-SOURCES.md 或模块设计规格，也不运行 components-readiness。

## 5. 代码边界规则

### 5.1 组件

出现两次只是观察信号，不是抽取规则。只有抽取后形成稳定、可命名、可独立变化的概念时才创建公共组件。

考虑拆分的证据包括：独立业务或交互责任、不同变化原因、多个真实消费者依赖同一稳定契约，或独立测试与渲染边界有实际价值。

不应拆分的信号包括：只为减少行数、只增加 Props 透传和跳转阅读、相似 UI 属于不同业务概念，或子组件仍依赖父组件私有逻辑。

### 5.2 Hook

Hook 用于封装内聚的状态、副作用和生命周期，或为多个真实消费者提供稳定契约。固定行数、一次使用的简单取值、格式化或事件处理，以及仅把页面代码移动到 hooks 目录，都不是抽取理由。私有 Hook 与拥有它的组件共置。

### 5.3 状态

| 状态类型 | 默认所有者 |
| --- | --- |
| 单组件的展开、输入或临时选择 | 该组件或共置 Hook |
| 多个兄弟必须协调修改的状态 | 最近的真实公共所有者 |
| 可分享、可刷新恢复的导航状态 | URL 或 Router |
| 服务端数据、加载和缓存状态 | 项目既有 server-state 工具 |
| 跨距离消费且需跨页面生命周期保留的状态 | 既有 Store 或 Context |

页面容器默认只负责路由、页面级错误边界、真实跨区域协调和模块组装。查询、表单、弹窗及局部交互状态不因页面容器身份自动提升。

### 5.4 性能

不在方案阶段预先穷举 memoization 热点。只有测量显示真实热点，或稳定引用是已确认的子组件或库契约前提时，才使用 React.memo、useMemo 或 useCallback。Reviewer 同时检查缺少有证据的优化和没有证据的优化。

## 6. 角色边界

- Orchestrator：维护需求基线、依赖图和并行批次，合并用户问题，发送最小上下文。
- Requirements Analyst：只负责业务需求和验收清晰化；设计稿仅作为需求证据。
- Technical Lead：拆工作包，识别共享契约、文件冲突、依赖和并行批次；Multi 不自动令每个包升级 Standard。
- Architect：只处理真实共享契约、高风险状态模型和跨工作包不变量，不逐页面设计完整组件树。
- Developer：拥有工作包内部实现、测试和自检；遵循现有项目结构，不强制完整技术分层。
- Reviewer：只审触发风险和受影响代码；重复两次、固定行数、未抽 Hook 或未加 memoization 不能单独构成问题。

## 7. v2 产物

| 场景 | 默认产物 |
| --- | --- |
| Direct | 无方案文件，仅保留变更和运行证据 |
| 单工作包 Fast | 一份精简 PLAN.md |
| Standard | 同一 PLAN.md 增加真实风险和回滚内容 |
| Multi | 精简 TASK-BREAKDOWN.md 和各包最小执行上下文 |
| 共享契约 | 仅记录共享类型、API、状态或稳定 UI 契约 |
| 条件 Review | 无问题只输出会话结论；有问题才持久化 |

Fast PLAN 目标不超过 80 行，Standard 目标不超过 120 行。行数只控制产物预算，不用于代码拆分。scheduleVersion 只在实际重编排时记录。Fast 同一 Agent 连续实施时不生成 HANDOFF.md 或 COMPONENT-SLICE.md。

## 8. 兼容与按需加载

- 主 SKILL.md 只保留 v2 默认调度、边界规则和路由条件。
- 旧版 Rigorous 规则移入 references/legacy-rigorous.md，仅在恢复旧运行或用户明确要求旧流程时读取。
- 现有旧模板与 validate-artifact.js 保留；v2 新运行不默认调用。
- Agent 文件只保留该角色独有的职责、输入、停止条件和输出，不复制主 Skill 全文。

## 9. 测试

v2 行为测试必须证明：

- 需求基线先于工作包拆分。
- UI 开发前存在 provided-specific 或 use-current-basis 用户选择。
- use-current-basis 后纯视觉粒度不再阻塞。
- v2 不生成设计覆盖矩阵且不运行 components-readiness。
- 安全独立工作包进入同一并行批次，且不存在逐包启动门禁。
- 活动提示词没有次数、代码行数或无证据 memoization 规则。

旧产物校验器测试继续保留。流程测试从指定句子匹配改为关键决策与禁止行为检查，并增加主 Skill 和 Agent 文件大小预算。

## 11. 验收标准

1. UI 开发前询问用户提供具体设计稿或按现有依据继续。
2. 需求阶段不判断设计稿的开发完整性。
3. v2 不生成设计覆盖矩阵、DESIGN-SOURCES.md 或模块设计规格，不运行 components-readiness。
4. use-current-basis 后纯视觉细节不再阻塞。
5. 同批安全工作包可同时开发，不被逐包用户验收串行化。
6. 活动提示词不存在次数、代码行数或文件大小驱动的组件与 Hook 拆分规则。
7. 页面容器不默认拥有全部查询和子组件私有状态。
8. memoization 只由测量或稳定引用契约触发。
9. 旧产物校验器和兼容测试仍通过。
10. 默认提示词显著缩小，并有自动化预算测试防止回归。

## 12. 预计收益

活动提示词和 Agent 指令预计减少约 1,300 至 1,700 行。普通 UI 工作包不再生成设计矩阵、模块规格或补水校验回环。组件、Hook 和状态归属由变化边界和理解成本决定，减少无意义文件、Props 透传与父组件膨胀。
