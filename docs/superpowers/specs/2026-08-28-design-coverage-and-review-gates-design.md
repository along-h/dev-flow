# 设计覆盖门禁与审查处置统一设计

## 1. 背景

当前 Dev Flow 存在两个直接影响交付质量的问题：

1. 架构师产出的组件拆分和技术方案没有用带职责备注的目录树直观表达最终文件边界，用户难以确认每个组件与文件的用途。
2. 用户提供大模块设计稿后，开发阶段可能直接进入实现，没有逐个核对可见 UI 组件的精确设计节点和状态，导致最终 UI 依赖推断，无法稳定做到 1:1 还原。

同时，架构对抗审查和代码与交付质量审查的处置规则不一致：前者由用户选择修改项，后者仍会让 P0 自动进入修复队列。流程需要统一为“审查完整呈现、用户决定是否修改、修复后限定范围复审”。

## 2. 目标

- 架构师在组件拆分和技术方案中输出完整目录结构，并备注每个目录、组件和文件的职责、变更类型与工作包归属。
- 取消 TDD 和全局共享架构的架构对抗审查，仅保留方案结构校验与用户确认。
- 建立可见 UI 组件级设计覆盖矩阵；开发前必须取得精确设计节点和状态规格，或获得用户逐项豁免。
- 自动从已提供的大模块设计稿中定位子节点，仅将无法定位的缺失项一次性询问用户。
- 开发完成后的代码与交付质量审查完整保留；P0、P1、P2 均由用户决定是否修改。
- 用户未选择修改项或明确说“跳过此次修改”时，记录残余风险并继续。
- 用户选择修改后执行修复，并只复审选中且实际修改的事项及其直接影响范围。

## 3. 非目标

- 不取消代码与交付质量审查、运行验证、工作包验收或最终用户验收。
- 不要求为 Hooks、services、types、测试等非视觉文件提供设计稿。
- 不根据本次调整修改历史运行产物或历史设计文档。
- 不允许开发者用相似页面、个人经验或项目默认样式替代缺失的精确设计事实。

## 4. 新流程

```text
需求基线与工作包拆分
          ↓
架构师输出组件拆分、技术方案、职责目录树、设计覆盖矩阵
          ↓
结构校验
          ↓
用户确认架构方案
          ↓
开发前设计补水门禁
  ├─ 自动定位大稿中的 UI 子节点
  ├─ 刷新组件级布局、尺寸、状态和文字处理规格
  └─ 一次性询问仍缺失的小模块设计稿
          ↓
全部 UI 组件 complete 或逐项 waived
          ↓
按精确设计规格 1:1 开发
          ↓
代码与交付质量审查
          ↓
用户选择修改项
  ├─ 无选择 / 跳过此次修改 → 记录残余风险并继续
  └─ 有选择 → 仅修复选中项 → 限定范围复审 → 再次由用户处置新问题
```

## 5. 架构产物调整

### 5.1 职责目录树

`COMPONENTS.md` 和 `TDD.md` 必须包含当前工作包的“职责目录树”；存在共享边界时，`GLOBAL-ARCHITECTURE.md` 还必须包含共享文件的职责目录树。目录树列出当前方案涉及的新增、修改、复用和保持不变的关键文件。TDD 可以细化已确认的组件目录树，但不得静默改变组件职责；发生职责变化时必须返回组件方案确认。

```text
src/
├── modules/
│   └── TabBar/                         # [复用][共享] 跨模块页签；当前工作包只扩展配置与图标
├── pages/student/home/                 # [不变][WP01] 学生首页入口，不修改周报模块
│   └── components/
│       └── VocabularyStudyCard/        # [新增][WP01] 首页词汇学习卡片，承载当前工作包 UI
│           ├── index.vue               # [新增][WP01] 卡片布局、状态展示与用户交互入口
│           ├── types.ts                # [新增][WP01] Props、视图状态和事件类型
│           ├── hooks/                   # [新增][WP01] 卡片内部状态与副作用
│           └── services/               # [新增][WP01] 卡片专属数据访问边界
└── pkg-stu/pkg-vocabulary/             # [修改][WP01] 学生词汇分包
    ├── index.vue                       # [修改][WP01] 词汇 Tab 根页面
    └── types.ts                        # [修改][WP01] 分包公共输入输出类型
```

每一项必须说明：

- 变更类型：`新增`、`修改`、`复用`、`不变`。
- 所属边界：工作包编号或共享边界。
- 单一职责：该目录、组件或文件在方案中的作用。
- 复用约束：复用文件允许调整的范围；不变文件明确禁止修改的范围。

目录树必须与组件树、数据流、接口契约和预计修改文件一致。开发发现需要新增目录树之外的文件，或改变已确认职责时，必须暂停并重新向用户确认受影响的架构章节。

### 5.2 设计覆盖矩阵

架构师从页面组件树中提取所有可见 UI 组件，在当前工作包的 `COMPONENTS.md` 中维护设计覆盖矩阵。`TDD.md` 引用该矩阵并记录确认版本，不重复维护第二份矩阵；全局共享架构只记录共享可见组件的设计归属，具体设计覆盖状态仍由使用它的工作包矩阵管理。

| UI 组件 | 文件路径 | 所属工作包 | 精确设计节点 | 必需状态 | 完整度 | 处置 |
|---------|---------|-----------|-------------|---------|--------|------|
| VocabularyStudyCard | `.../VocabularyStudyCard/index.vue` | WP01 | 可回查节点链接 | normal/loading/empty/error | complete | 按规格开发 |
| WordDetailModal | `.../WordDetailModal/index.vue` | WP01 | 尚未定位 | normal/loading/error | blocked | 开发前补充链接 |
| `types.ts` | `.../types.ts` | WP01 | 不适用 | 不适用 | not-applicable | 非视觉文件 |

完整度只允许：

- `complete`：精确节点可回查，布局、尺寸、颜色、字体、间距、状态和文字处理规格完整。
- `blocked`：存在无法从有效设计源确定的视觉事实，禁止进入该组件开发。
- `waived`：用户明确豁免该组件设计稿，并记录原话、残余风险和人工视觉验收项。
- `not-applicable`：非视觉文件，不需要设计稿。

## 6. 取消架构对抗审查

TDD 和全局共享架构不再执行独立架构对抗审查，也不再产出以下内容：

- `BLOCK`、`ACCEPT_WITH_RISK`、`ACCEPT` 架构审查结论。
- `AR-xx` 架构问题编号。
- 架构审查问题处置表。
- 架构修订后的对抗复审回环。

新的架构门禁为：

1. 架构师完成组件拆分、职责目录树、技术方案、风险评估和设计覆盖矩阵。
2. 产物通过结构与一致性校验。
3. 主 Agent 向用户展示目录树、职责、设计覆盖缺口、风险和方案摘要。
4. 只有用户明确确认后才能进入开发前设计补水。

用户确认不能把 `blocked` 的设计覆盖项变成 `complete`。设计事实仍必须通过精确节点补齐，或由用户对具体组件明确选择 `waived`。

## 7. 开发前设计补水门禁

### 7.1 自动定位优先

开发者先读取已确认的职责目录树和设计覆盖矩阵，再使用现有顶层设计源自动定位每个可见 UI 组件的精确子节点。能定位时直接刷新模块规格，不向用户重复询问。

自动定位必须保存：

- 顶层设计源和精确子节点链接。
- 节点名称、层级路径和提取时间。
- 布局、尺寸、颜色、字体、间距、圆角、阴影和文字溢出规则。
- normal、hover、active、focus、disabled、loading、empty、error 中适用的状态。
- 响应式断点和各断点差异。

### 7.2 缺失项集中询问

自动定位结束后，主 Agent 将所有仍为 `blocked` 的 UI 组件一次性列给用户。每项说明组件名称、所在页面、已有设计源、缺失事实和需要的精确模块链接。不得逐个零散询问，也不得询问非视觉文件。

用户补充链接后重新提取；用户也可以对指定组件明确选择 `waived`。没有明确豁免时，沉默不能视为放弃设计稿。

### 7.3 开发准入条件

只有设计覆盖矩阵不存在 `blocked` 项时才能开发。开发期间必须按组件逐项对照规格实现，不得自行猜测缺失尺寸、颜色、间距或状态。

## 8. 代码与交付质量审查处置

首轮代码与交付质量审查仍覆盖当前工作包完整变更、验收标准、风险、设计还原度、测试和运行证据。审查问题继续使用 P0、P1、P2 表达影响级别，但级别不再自动决定是否进入修复队列。

审查完成后：

1. 主 Agent 必须一次性呈现全部 P0、P1、P2 问题、证据、影响、修改建议和残余风险。
2. 用户逐项选择是否修改，或明确说“跳过此次修改”。
3. 只有用户选中的问题进入修复队列。
4. 没有问题时记录 `NO_CHANGES_REQUESTED`。
5. 有问题但用户全部不选，或明确跳过时，记录 `WAIVED_BY_USER`、用户原话和残余风险，然后继续下一阶段。
6. 用户对问题处置的确认不等同于多工作包的工作包验收；需要工作包验收时仍单独等待用户确认。

## 9. 修复与限定范围复审

开发者只修复用户选中的问题，不处理未选问题。修复完成后必须增加一轮复审，复审输入限定为：

- 用户选中的稳定问题编号。
- 针对这些问题实际修改的文件和逻辑。
- 修改项的直接调用方、直接数据契约和直接受影响测试。
- 本轮重新运行的受影响检查与测试证据。

复审不得：

- 重新全量审查当前工作包。
- 重复输出已关闭且未受影响的问题。
- 重新提出用户已经放弃且未被本轮修改影响的问题。
- 因修复顺手扩大到需求范围外的代码。

若在直接影响范围内发现修复引入的新问题，Reviewer 使用新稳定编号记录，并再次交给用户选择是否修改。若修改暴露出工作包范围、接口契约或架构方案必须变化，停止修复回环并返回对应架构确认阶段，不以扩大复审范围代替重新确认。

## 10. 产物与校验调整

### 10.1 需要修改的当前产物

- `SKILL.md`：状态机、阶段定义、架构门禁、开发设计补水、代码审查处置和复审范围。
- `README.md`：公开流程、治理路径和审查语义。
- `agents/architect.md`：职责目录树和设计覆盖矩阵要求；删除架构对抗审查职责。
- `agents/developer.md`：按 UI 组件执行自动定位、集中补水和开发准入检查。
- `agents/code-reviewer.md`：删除架构审查模式；统一全部级别的用户处置；限定复审范围。
- `templates/components-template.md`：增加职责目录树和设计覆盖矩阵。
- `templates/tdd-template.md`：保留技术方案确认，删除架构对抗审查与处置章节。
- `templates/global-architecture-template.md`：保留技术方案确认，删除架构对抗审查与处置章节。
- `templates/review-report-template.md`：增加统一用户处置记录和限定复审输入。
- `scripts/validate-artifact.js`：校验职责目录树、设计覆盖矩阵、用户方案确认、代码审查处置和限定复审输入。
- `tests/`：覆盖新产物契约和新门禁行为。
- `manifest.json`：删除架构对抗审查能力描述，补充设计覆盖门禁。

### 10.2 校验行为

- `components`、`tdd-proposal`、`tdd`、`global-architecture-proposal` 和 `global-architecture` 校验各自适用的职责目录树及逐项备注。
- `components` 校验设计覆盖矩阵存在且状态合法；`tdd` 校验已引用并记录用户确认的矩阵版本；全局架构校验共享可见组件已明确归属到具体工作包矩阵。
- 最终 TDD 和全局架构只校验用户确认记录，不再要求架构审查章节和结论。
- `review` 要求存在审查问题处置章节；有问题时必须记录用户决定。
- 第二轮及以后要求 `incremental`，并记录用户选中修改的问题、本轮实际修改项、直接影响范围和相关测试证据。

## 11. 测试策略

采用测试先行：

1. 先增加会失败的产物校验测试，证明旧校验仍接受缺少职责目录树、设计覆盖矩阵或用户处置的产物。
2. 增加最终 TDD 和全局架构无需架构对抗审查、但必须有用户确认的通过用例。
3. 增加 `blocked` UI 设计项阻止开发准入的用例；`complete`、逐项 `waived` 和 `not-applicable` 允许继续。
4. 增加 P0 未经用户处置不能完成审查、P0 被用户明确跳过可以继续的用例。
5. 增加修复复审缺少用户选中项或直接影响范围时拒绝通过的用例。
6. 运行完整 `npm test` 与 `npm run check`，并执行模板产物校验。

## 12. 风险与控制

| 风险 | 控制措施 |
|------|---------|
| 取消架构对抗审查降低独立技术挑战 | 强化职责目录树、风险评估、结构一致性校验和用户方案确认；代码实现后仍进行完整质量审查 |
| 用户跳过 P0 后继续可能带来交付风险 | 必须保存用户原话、证据、影响和残余风险；最终交付不得把未验证风险描述为已解决 |
| 设计节点命名与代码组件不一致 | 使用页面位置、节点层级和视觉职责联合定位，并在设计覆盖矩阵保留可回查链接 |
| 设计询问过于频繁 | 自动定位优先，所有缺失项一次性询问，非视觉文件不询问 |
| 修复引发架构变化 | 停止限定复审并返回架构确认阶段，不静默扩大修改或复审范围 |

## 13. 验收标准

- 架构产物能够以带备注目录树清晰展示每个计划文件的作用、变更类型和工作包边界。
- TDD 和全局架构流程不存在架构对抗审查阶段、章节、结论或问题处置回环。
- 用户确认架构后，开发仍会在所有 UI 设计项完整前被门禁阻止。
- 大设计稿中可自动定位的子组件不会重复询问用户；无法定位的组件会一次性集中询问。
- 所有可见 UI 组件均有精确设计节点与适用状态规格，或有用户逐项豁免记录。
- P0、P1、P2 都不会自动进入修复队列，均由用户选择。
- 用户全部不选或说“跳过此次修改”时，流程记录残余风险并继续。
- 修复后必有复审，且复审只覆盖选中并实际修改的事项及直接影响范围。
