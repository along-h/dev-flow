> 全部 P0/P1/P2 审查完成后由主 Agent 一次性呈现给用户。每个真实问题标题必须严格使用 `### P0-1/P1-1/P2-1` 稳定唯一编号；未编号或重复编号的候选必须打回。任何级别都必须等待用户决定后才能进入修复；每个问题必须记录用户决定。
> Reviewer 输出候选时不代填用户决定；候选先通过 `review-proposal`。主 Agent 收到用户决定后逐稳定编号填写下表，再通过 final `review` 校验。

## 用户处置与限定复审规则

1. 主 Agent 在审查完整结束后，一次性呈现全部 P0/P1/P2 的证据、影响、可执行修复方案和残余风险。
2. 只有状态为 `SELECTED_FOR_REVISION` 的问题进入修复；开发者不得处理未选问题。
3. 修复后必须执行 `incremental` 复审；本轮实际修改编号集合必须非空且为用户选中编号集合的子集。直接调用方、直接契约、直接受影响测试三类分别填写具体值或“`不适用：可核验证据原因`”，并附本轮新鲜运行证据。
4. 复审不重复输出已关闭且未受影响的问题，也不重新提出用户已放弃且未受本轮修改影响的问题。
5. 直接影响范围内发现的新问题使用新编号，并再次由用户决定是否修改。
6. 架构、接口契约或工作包边界必须变化时，停止修复并返回对应架构确认阶段，不扩大复审范围。

> `multi-workstream` 的工作包验收是独立门控。审查问题处置完成不等于用户已接受当前工作包。
